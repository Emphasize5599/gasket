# On-device AI: agreed model and implementation contract

Decision recorded 2026-10-15 against `ae87187` on `test/keyless-regular-gas`; initial native integration added in 0.0.159. TODO.md remains the only active backlog. Item 38 retains real-phone/model acceptance; items 32 and 42 remain future work, not implemented onboarding or complex-case fallback screens.

## Implemented in 0.0.159

1. `GemmaService` owns an opt-in native preference, one serial worker, a generation deadline and cancellation epochs. `GemmaRuntime` uses LiteRT-LM 0.18.0, tries GPU then CPU on initialization failure, streams text without thinking channels, and unloads after an idle minute. Context grows conservatively with input size (8k–32k); complete UTF-8 prompts above 27,000 bytes are refused, never truncated. Output is bounded to 2,048 tokens; generation/load cancellation is requested after two minutes. Native initialization itself is not safely interruptible; the UI stays asynchronous and cannot start another generation until native work unwinds.
2. Settings (not first-run onboarding) has enable/disable, explicit 3.66 GB download consent, cancel/resume and removal controls. `ModelDownload` streams to durable no-backup storage, checks HTTP ranges/length/free space, verifies SHA-256 and atomically promotes a completed file. The APK contains the runtime, not the weights. A restored ordinary settings file cannot trigger a model download. A killed/background process can interrupt the download; resume is manual, not an Android foreground-download service.
3. `TirePolicy` supplies the same versioned branches, current shared spread limits, full relevant per-position setup and evaluated findings used by the advice UI. It identifies affected tires, leaves missing manufacturer/pattern information unknown, and requests fitment review rather than inventing exact rotations. `Gemma` coalesces requests to the current setup, rejects stale replies and caches by full policy/input/model fingerprint. It schedules early on garage changes without blocking route progression.
4. JSON validation requires every supplied fact/action ID exactly once, rejects unapproved actions and screens generated prose for invented numerals, markup/links and action/safety language. App-owned actions and tire notices remain independently visible. **These are bounded output guards, not proof that free prose is semantically correct.** Real-model answer quality and rejection rates need phone evaluation. Without a valid explanation the existing checked notices remain; item 42's richer fallback responses are not implemented.
5. `Tasks` combines station progress, larger-model download/verification/load/generation and lightweight AI preparation/rating. A rounded-square arrow appears only for multiple active tasks and takes its own flex space to the bar's right. Expanding shows the remaining tasks with their own progress/cancellation controls; generation/loading uses indeterminate progress. AI tasks do not acquire station-search data locks. Settings/submenu headers reserve room for the top bar. Station searches retain existing inline-progress behavior when they are the only active task.
6. Gradle 8.13 / AGP 8.13.2 package the native AAR and pinned transitive dependencies; `build.sh` retains existing signing and direct APK output. The original manifest remains the package/version source. A build task verifies the native AAR checksum and bundles its complete license/third-party notices plus resolved Java dependency notices; project information opens the full texts on demand.
7. Automated checks: `gemma` covers policy/validation; `gemma-ui` covers consent, mock-engine serialization, editing and disable/cancel; `tasks` covers 320/448px multi-task layout, progress and locks; `gemma-native` compiles the actual streaming downloader against small local HTTP fixtures. No real model is downloaded in CI. These do not substitute for the remaining phone acceptance in TODO 38.

## Model responsibilities

1. Keep `Xenova/all-MiniLM-L6-v2` for the existing embedding/similarity work in `assets/web/severity.js`. It compares text; it cannot compose advice. Use deterministic source flags and numerical calculations ahead of any model when those already answer the question.
2. Use **Gemma 4 E4B instruction-tuned** for dynamic, whole-setup explanations that need generated language. Do not send routine ratings through it merely because it is available. First integration target: tire advice, not arbitrary chat or autonomous changes to the vehicle/route.
3. Run **one larger-model task at a time**, using one native engine and a bounded, coalescing queue. This is a generation-concurrency limit, not a reduction of the user's station-reader setting. Do not retain an unbounded queue of obsolete requests.

## Native integration and download

1. Use Google's [LiteRT-LM Android runtime](https://developers.google.com/edge/litert-lm/android). Version 0.0.159 replaces the former Gradle-free pipeline with a dependency-aware build for `com.google.ai.edge.litertlm:litertlm-android:0.18.0`; preserve application identity, existing signing key, API budgets, direct APK release assets and fast cached CI. Do not hand-merge arbitrary AARs into the old dex pipeline.
2. Initial candidate is the standard CPU/GPU-compatible [`gemma-4-E4B-it.litertlm`](https://huggingface.co/litert-community/gemma-4-E4B-it-litert-lm/tree/2eee7ac325f20eb8c9ac1d0e972f7c84663062da), not the separate web or GPU-only variants. Verified revision: `2eee7ac325f20eb8c9ac1d0e972f7c84663062da`; bytes: `3659530240` (about **3.66 GB**, not the smaller text-decoder weight size); SHA-256: `0b2a8980ce155fd97673d8e820b4d29d9c7d99b8fa6806f425d969b145bd52e0`. Verify these again when implementing, and change the pin deliberately rather than following a moving main revision.
3. Download only with explicit consent. Show size, progress, cancel and network-use guidance; resume interrupted downloads only with correctly validated HTTP ranges, verify length/checksum before atomic promotion, and check free storage including partial-file overhead. Partial/corrupt downloads must never count as ready. Never bundle gigabytes of weights into the APK or full backup. Use durable no-backup storage, not cache, and offer removal of the downloaded model.
4. Default larger-model mode off. Restoring a preference must not silently trigger a multi-GB download. Enabling/disabling must be honored natively as well as in JavaScript; unsupported ABI/backend failures should fall back without crashing an otherwise usable app.
5. Load and generate off the UI/WebView thread. Try a supported accelerated backend, with a controlled CPU fallback; benchmark on the user's phone rather than transferring another device's published performance figures. Disable unused vision/audio paths. Begin with bounded context/output, low-variance sampling and no unnecessary thinking-token budget; measure before enabling speculative decoding.
6. Cancel obsolete work after a vehicle/setup change. Key results by model revision, policy version and complete relevant input fingerprint; discard results from a prior setup even if they arrive after a newer request. Never cache only by vehicle ID. Unload idle native resources on a measured policy, and release them when disabled or the activity is destroyed. Cancellation and lifecycle races need explicit tests.

## Explain from checked facts, not memorized vehicle specifications

The user's intent is concise, complete explanations of dynamic situations rather than a hardcoded wall of prose. Supplying all relevant if/then rules helps, but **a prompt alone cannot guarantee compliance or eliminate hallucinations**.

1. Establish a versioned rule representation shared by evaluation, prompt construction and validation. Do not maintain an independent prose copy of the rules that can drift from `TireMath`. Address the known item-36 replacement/rotation defect before elevating existing outputs to authoritative inputs. Treat current generalized tread/spread assumptions as app heuristics, not manufacturer-specific limits.
2. Supply the entire relevant setup and applicable branches, including unknown values: drivetrain and its certainty; front/rear sizes; per-position brand/model/type; same-set versus individual tires; dually inner/outer positions; attached trailer and axle layout; measured or estimated depths; tire mileage, rotation history and warranty assumptions; supported pattern/directional/staggered restrictions; known spare facts. Do not send VINs, API keys, unrelated logs, trip locations or the full backup when tire advice does not need them. Do not invent absent age, pressure, load, pattern or manufacturer data.
3. Include every applicable evaluated fact, its stable ID, severity and provenance. Include missing-data facts explicitly. All safety-critical applicable branches must fit: if the complete relevant policy/setup exceeds the model's supported context, partition by validated scope or return the fallback, **never silently truncate it**. Data from websites and user labels is untrusted data, not instructions.
4. Ask for a short overall recommendation, a useful ordering of actions and necessary caveats. Require structured action/fact references and explicit unknowns alongside any generated prose. Appropriate brevity is outcome-based: no repeated warnings, but no hard sentence limit that removes a material fact.
5. Validate referenced tire positions, facts, action eligibility, numbers and required-warning coverage against the actual snapshot. Reject unsupported replacement/rotation actions and invented manufacturer requirements. Keep mandatory safety notices visible separately from AI prose: structured references alone cannot prove free text is correct. If an explanation is unsupported, contradictory, truncated, malformed or late, use the deterministic fallback. Do not automatically apply any generated recommendation.
6. Label accepted generated text as AI-written and preserve the measured/estimated distinction. Equal tread depths must not imply matching tread patterns; unknown drivetrain must not imply two-wheel drive; AWD must not imply an unconditional replace-all rule. When the app cannot establish a safe answer, name the uncertainty and the appropriate inspection/manual check instead of inventing certainty.

## Scheduling and user experience

1. Prepare and deduplicate inputs as soon as the relevant setup is stable, without waiting for the Advice menu to open. Prioritize the currently selected vehicle/current planning step; cancel superseded jobs. Keep station discovery, forecast fetching and the UI responsive while generation runs. Do not make the user wait for optional prose before starting a route.
2. Show a subtle in-progress state where advice will appear; retain the existing checked notices during generation. Avoid repeated failure toasts or an endless spinner. An explicit useful deadline must lead to fallback, even if native cancellation completes later.
3. Onboarding offers the larger model and its benefits, download size and controls. Use the existing native `memoryInfo()` RAM detection. Warn for low detected RAM using a clearly documented, device-tested heuristic; RAM amount is not a guarantee of speed or success. Do not prohibit use based solely on the warning, and do not report unknown memory as low.
4. When disabled or unavailable, give useful concise fallback advice with known facts, safe next steps and missing information. The user should not need the larger model to receive safety information. More capable complex-case fallback writing is tracked as TODO 42, not assumed to exist already.

## Acceptance and licensing

1. Test with a fake native engine for queue serialization, cancellation, stale replies, disable/restore, context overflow and cache invalidation. Test the downloader separately with small fixtures for resume, corrupt bytes, low storage and interrupted promotion. Do not download the real multi-GB model for every CI run.
2. Test advice against a scenario matrix: FWD/RWD/AWD/unknown; mixed front/rear wear; matching depth with different patterns; missing details; directional/staggered restrictions; dually inner/outer positions; trailer tires; prompt-injection-like labels; malformed output, unsupported facts and missing warnings. Tests verify the evaluator/validator and that fallback remains usable; passing them does not establish free-text correctness for every real case.
3. Before declaring the integration usable, perform real on-phone model download/load/generation tests, cold/warm timing, GPU-to-CPU recovery, cancellation and app lifecycle checks, alongside a large station scan. Record whole-process/native memory and responsiveness, not just Java heap. Measure concise-answer quality and omissions with the real model. Published benchmarks do not establish Gasket's latency or hardware compatibility.
4. The selected [conversion](https://huggingface.co/litert-community/gemma-4-E4B-it-litert-lm) and [upstream model](https://huggingface.co/google/gemma-4-E4B-it) identify Apache-2.0 licensing. Preserve required licenses/notices for model distribution/download and the native/transitive runtime dependencies. Version 0.0.159 bundles the runtime's license and complete native THIRD_PARTY_NOTICE.txt, as well as resolved Java dependency notices. Put brief project credits/legal details in the existing project information, not release-note credit lists.
