# Overnight rest planning (314)

Route → Flexible trip timing has a Planning mode selector above Plan within a time window. The existing arrival/departure workflow is unchanged by default. Plan around overnight rests uses the same required departure or final-arrival window and optional opposite-time constraint. Nightly rest defaults to22:00–08:00 local to each stop, minimum6h/preferred8h. Individual-night overrides use the local date on which the night starts. Both durations must fit the selected nightly hours; preferred cannot be below minimum. The existing calendar/time-wheel UI handles these fields.

Find overnight rest options reads the shared persistent NTAD/OSM/RIDB inventory and source filters, including saved user edits. Time zones are batched and persisted through StopClock. Candidates without a known time zone cannot qualify. Hourly departures are compared on the currently selected roads; choices are estimates, not a proof of optimum across all roads or campground inventory. Proposals rank the minimum per-night choice count, total choices, preferred-rest shortfall, then estimated duration/known fees and departure. It selects a forward sequence greedily, not an exhaustive product of all campsites. The user can change each proposed site before approval; subsequent verification recalculates the sequence and rejects incompatible selections.

A rest is required when continuing would pass the end of that night's hours minus the minimum rest. Short trips finishing before that point need no added stop. Rests begin on arrival within the nightly interval and take preferred duration if possible, otherwise at least minimum. Date/time conversion uses stop-local calendars and actual elapsed time through daylight-saving transitions. Known closure, vehicle exclusion, parking/arrival-gate hours and maximum stays exclude candidates. Unknown permission/hours never become confirmed facts. Every proposed stop requires an explicit permission/reservation acknowledgement, including non-private sites. Nothing books a campsite.

Before applying, verify selected road-access geometry and total detour against the independent rest-stop detour limit. Recompute each arrival and rest period in sequence. Recreation.gov selections additionally require current structured facility/gate/closure/amenity/rate/calendar eligibility via the existing Recreation evaluator. Final-arrival constraints include the dwell and access estimates. Failure/cancellation leaves the original itinerary intact. Partial inventory coverage is shown. Applying is transactional: splice verified access paths into selected roads, preserve station inventory, remap destination windows/EV destination configurations, record overnight dwell and permission in the saved trip, and fix the selected departure. Replacement removes previous generated rests rather than duplicating them; changed roads require removing the old generated rests before replacement to avoid overwriting explicit edits.

The approved proposal returns to Route. The existing hourly hazard approval and full station/fuel/traffic planner run afterwards. Final planning checks actual dwell, minimum rest, nighttime end, site opening/calendar data and all arrival/departure windows. Fuel/charging delays and traffic may invalidate a preliminary proposal; the app must report that rather than silently shorten a rest or bypass hazard review. Initial proposals do not yet model all fuel/charging stops, intermediate destination waits or every tariff; they are clearly labelled estimates until normal planning succeeds. The feature does not claim exhaustive optimum campsite availability, current occupancy, guaranteed access or reservations.

Tests: overnight exercises threshold/rest fitting, repeated nights, overrides, stay/access/hour exclusions, arrival including dwell, DST and cancellation. overnight-ui at320/448 exercises final-arrival vs departure anchors, form errors/overrides, explicit approval, road-access failure leaving the route untouched, one/two-night persisted insertion and replacement without duplicates. Existing window form, hourly hazard/window planner, recommendations/performance, rest and traffic-refresh regressions are retained. Phone checks: select overnight mode for a long trip; set an anchor and nightly preferences; inspect local arrival/leave times, switch a campsite and confirm permission; approve then complete hazards/planning; save/reopen and replace once; test unavailable sites and a tight final-arrival window.

## Chronological window editor (315)

Trip-wide cost/time, traffic tolerance and nightly-rest controls sit above the numbered journey. Origin offers only an optional departure tile, intermediate destinations offer independent arrival/departure tiles, and final endpoint offers only arrival. An enabled tile requires earliest/latest values; at least one complete origin-departure or final-arrival anchor is needed. Intermediate windows are not compulsory. Blank new setup no longer invents a window. Pair edits keep earliest/latest ordered; obvious backwards endpoint/destination combinations are rejected. The editor normalizes into the existing planner schema, preserving arrival-only and both-anchor plans. Explicit destination departure windows override immediate-return behavior during window planning. Collapsed headers show saved time ranges.

## One-sided windows and location clocks (317)

Supersedes315’s required pairs for newly edited windows. Final latest-arrival is required; final earliest-arrival is optional. Both origin bounds are optional, with earliest departure defaulting to now. Enabled intermediate arrival/departure controls require at least one bound. Blank intermediate lower/upper bounds normalize to the departure lower bound/final deadline for the existing planner, while the original empty input is retained for editing. The finite search is at most14 days from effective earliest departure through final latest arrival. The live default-now placeholder uses the origin time zone; its planning instant freezes when hourly screening starts. No extra search-range display is added.

Time zones come from route-stop coordinates via the existing persisted/batched StopClock service. Form values use each point’s IANA zone, not the device zone, and are saved as absolute UTC instants plus point zones. Unknown zones block save and offer retry. A DST gap is invalid; a repeated wall time requires explicit first/second occurrence selection, preserved on reopen. Calendar validation uses the control’s zone. Device zone/offset changes are detected on focus/visibility and every30 seconds and logged; they do not reinterpret saved instants. Leg departures/arrivals and hourly hazard labels show the respective local zones. Historical device-local window values are anchored to the device zone on first loading in this version; invalid/ambiguous legacy values require review. No original-zone inference is possible for old files that lacked it.

Focused verification includes deadline-only full trip planning; Central/Eastern equal instants; Phoenix and fractional offsets; invalid and repeated DST wall times; a real browser device-zone change toTokyo with unchanged NY appointment; source-zone failure; intermediate one-sided inputs; calendar device/point-zone gap differences; existing hourly, rest, overnight and traffic-cache workflows. Phone checks should include a Central→Eastern trip, destination deadline-only, save/reopen after a device-zone change and the default-now label.

Inserted overnight points retain their own time zone and rebuild the indexed metadata; hazard and Depart labels read the actual current point/rest site, so adding/removing stops cannot shift zone labels onto another destination.316 was cancelled before APK publication;317 contains the completed change.

## Overnight rests in Stops (318)

Supersedes the 314 Route-step proposal/approval. Nightly preferences stay in the time-window form, but no stops are chosen before hazard review: roads, departure and fuel/traffic timing can still change there. Stops → Rest stops uses the preferences: a place is listed for the night when its estimated arrival (current plan, access detour and earlier added rests included) falls inside that night's hours with room for the minimum rest (`Overnight.fit`, the site's own time zone). The tile says where a night's rest becomes necessary (continuing would pass the night's end minus the minimum rest) until an added overnight rest covers that night. Show all rest stops lists the rest. Adding a fitting place prefills the minimum rest, keeps the stay inside the night and records it as an overnight rest; each addition rechecks the remaining places against the new timeline. Final planning still enforces the nightly hours and minimum rest. Permission, reservations and availability remain the user's to confirm.
