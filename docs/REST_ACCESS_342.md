# Rest-access throughput and explicit failures (0.0.342)

## Evidence
The owner's 341 log contains two large rest searches. Across the recent session there are 416 origin-timezone failures, 116 Recreation.gov cooldown warnings, three explicit HTTP 429 warnings, 27 HTTP 404 warnings and 734 detour-limit exclusions. The last background pass reports 1,480 processed out of 2,900 before being stopped. Processed did not mean verified. Two ResizeObserver delivery-loop errors were also recorded. Raw logs and personal trip data remain local and are not committed.

Bounded desktop probes made 36 requests to each of Open-Meteo, Recreation.gov and Google Maps traffic (108 total). Each provider was sampled with one, four and eight concurrent requests, 12 requests per stage. All returned HTTP 200 and structurally recognizable data; no refusal or Retry-After header was observed. At eight concurrent requests, the short bursts measured roughly 15.4, 24.8 and 10.0 requests/second respectively. Recreation.gov probes covered campground detail records, not every reservation endpoint. Google probes used the app's public anonymous directions request format; no cookies, credentials or verification bypass were used.

These small samples establish successful throughput on this desktop connection, not an exact universal rate limit. The phone log demonstrates that larger sustained bursts can be refused. Production uses fixed conservative bounds, not adaptive rate estimation: **six request starts per second and at most eight in flight**, independently for Google traffic and Recreation.gov. The selected reader counts can lower concurrency. Cached reads do not consume network slots. One bounded retry is allowed for transient errors; 404 is not retried. Rate-limit responses pause the queue and honor Retry-After, with a one-minute fallback. Google human-verification handling remains explicit.

Open-Meteo's [published free allowances](https://open-meteo.com/en/pricing) are 600/minute, 5,000/hour and 10,000/day. Missing traffic timezones are batched up to 20 points with two batches in flight. All rest/traffic timezone fetches now use the same weighted WeatherNet budget and persisted cooldown as hourly weather: 500/minute, 4,500/hour, 9,000/day. Every batched location consumes allowance. Existing weather use therefore cannot be ignored by a separate timezone client. Failures retain the actual service error instead of only “Origin timezone unavailable.”

## Changes
- Directed access geometry and durations use bounded persistent TrafficCache storage. Keys include provider, exact endpoints, direction, UTC departure minute and avoid flags. Expiry follows the selected traffic-cache policy. Cache hits need no timezone or routing fetch. Only validated successes are stored; permission, occupancy, opening hours and campsite availability are still checked separately. In-flight work is shared without one cancelled consumer poisoning another; clearing the cache prevents late replies restoring access entries.
- Traffic origins accept known IANA zones and read discovery's existing `restplaces/timezone` records. Newly resolved zones are shared back. Unknown origins still get a real lookup; a nearby site's timezone is never guessed across a boundary.
- Early geodesic detour rejection remains. An outbound route plus a conservative minimum return can now reject an excessive detour before the return request. Places with a stay limit below the UI's five-minute minimum are rejected early. Nightly fit and short detours influence priority; an otherwise valid short-rest candidate is not discarded just because it misses overnight preferences.
- Initial candidates are spread across each leg and interleaved between legs. Every remaining result is subsequently checked. Visible/tapped candidates keep their urgent priority. The access-check pool is also capped at eight sites, so a 50-reader setting cannot put 50 outbound reads ahead of the first return read.
- Progress distinguishes processed, verified, excluded, unavailable and cancelled work. Persistent incomplete-check messages remain on the rest tile and directory. Retry targets unavailable checks and keeps successful/excluded results. Failed or malformed access data never counts as verified. Periodic diagnostics report cache hits, requests, queue/provider times, timezone batching, fixed pacing, cooldowns, both reader settings and remaining work. No coordinates are added to those diagnostics.
- Task and submenu ResizeObservers defer layout writes to animation frames and avoid redundant header-style writes instead of suppressing delivery errors.

Automated coverage includes a 2,900-result ordering fixture; persistent access reuse, expiry and provider/direction/time/settings separation; cancellation and cache-clear races; fixed request spacing and Retry-After; shared timezone batching and weather accounting; visible failure counts and targeted retry at 320px. Desktop service probes are not phone benchmarks.

If a provider refuses requests, the cooldown and incomplete status should remain visible. Retry unavailable checks after the cooldown. Look for `Rest access progress`/`Rest road access checked` diagnostics rather than interpreting the processed count as success.
