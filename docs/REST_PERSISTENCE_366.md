# Rest-site reuse and refresh policy — 0.0.366

The owner reported 1,681 road-access resolutions on every trip using the same roads. The previous durable access entries were indexed by departure minute and competed with hourly traffic observations in an 8,192-slot cache. The UI's final eligibility records were only in memory. Different arrival minutes therefore missed the saved access, and large traffic searches could evict it.

Directed rest access now lives in the existing backed-up `restplaces` namespace, independently of forecast eviction and recent-trip records. Its identity includes provider, directed endpoints rounded to five decimals, and avoid-highway/toll/ferry settings. Departure time and vehicle energy settings are excluded. Cached geometry/timing is a reusable access estimate; departure-specific traffic forecasts retain their existing separate cache and matching rules.

Before queuing background checks, RestUI restores available access and reevaluates hours, stay limits, the current detour limit, user prices and date-specific Recreation.gov rules locally. Fully warm lists redraw immediately and start no bulk access task. Incomplete or failed lookups are not stored as successful access. Changing roads, directed endpoints, provider or avoidance settings requires compatible data. Increasing the detour limit can fetch a previously unnecessary return route.

`Settings → Rest stops → Refresh changing rest-site data every (days)` stores `S.restRefreshDays`, default 7, valid whole days 1–365. RV Parky/Campendium price-bearing cells and Recreation.gov rates, site status, facility notices/hours and date-scoped availability use this age on the next relevant search/use. Existing filter-scoped eligibility checks precede rate/calendar refresh. Newly required months still need their own availability records. Expired prices do not become verified on failed refresh; source timestamps and stored durable facts are retained. Area APIs can refresh an area rather than one campsite. This is demand-driven, with no periodic polling.

Durable campsite snapshots and fallback cell facts have no age cutoff. Successful Maps identities remain reusable until explicitly cleared/edited or the place identity changes; confirmed no-match results use the configured refresh age. Imagery thumbnail retrieval and departure forecasts keep their existing independent policies. Road access estimates use the configured age; the last successful geometry remains stored even when its estimate needs refreshing. An explicit data erase can remove stored information.

Migration scans old access entries still present in the traffic index, copies valid latest observations into the new namespace, preserves their original observation time, and yields every 32 records. It does not recreate already-evicted data. A shorter refresh interval immediately rejects older migrated observations; migration never renews freshness. Forecast entries are not deleted or rewritten by this migration.

Validation includes a 1,681-site browser scenario: cold load, a separate trip/date with zero additional access calls and no bulk progress task, then changed opening hours and stay limits evaluated locally. Actual TrafficFlow tests cover restart/date reuse, independence from traffic-index eviction, old-key migration without network reads, original age preservation, direction/avoid settings and expiry. Cache-policy tests cover weekly defaults, 14-day/1-day configuration, filter-scoped refresh and failure retention. Source-settings checks exercise valid/invalid intervals at 320/448 px. Physical-phone performance and provider behavior are not claimed from these fixtures.

Phone checks: load a route once, then plan another trip using the same roads. Within the configured age, existing successful access should be restored without another full road-check pass. Logs should include `Saved rest access reused` and, after upgrading, possibly `Saved road access migrated`. In Settings, change the interval and reopen it to confirm persistence. Missing/new/stale records can still require requests; do not clear stored data for this check.

## Later-leg forecasts and displayed times

The owner clarified that November 8 was probably the correct arrival at an original destination, rather than an incorrect onward departure. Original intermediate endpoints now show their actual planned **Depart** time, including multi-day waits; candidate/added rest stops and the final destination show **Arrive**. Added-rest management uses the rest's actual route mile for arrival, rather than mile zero.

Rest recommendations no longer depend on the entire route signature or leg number. Each key uses its own geometry, stable place facts, departure, destination window, filters/nightly hours/tolerance and provider settings. Completed suggestions survive an earlier insertion that renumbers an unchanged later leg. Place IDs and leg-relative distances remap result actions to the new inventory, avoiding stale array indices. Memoized dependency strings avoid rebuilding large keys per row. Expiry uses the oldest sampled forecast's age/preset; an unrelated daily inventory recheck does not invalidate still-fresh traffic recommendations. Partial cancelled work may restart, reusing available lower-level profiles.

## Hidden gas stations

“Don't use this station” also hides it from operational map/list/detail views, visible inventory, trip candidates, markers, stop cards, alternatives and top-ups. Previously saved comparison results are checked before display; a plan requiring a hidden station is marked for replanning instead of silently dropping a needed refueling stop. The existing station data remains in storage. Hidden-list management exposes anonymous entries with Use again; names, addresses and map-jump links remain hidden there too. Bad-CITGO discount eligibility is separate from hiding a station. Undo/restoring an entry allows it to appear again.

## Incremental initial traffic analysis

Completed successful traffic profiles now have an independent bounded `analysis-index`/`analysis-slot` cache. The index uses a short hash but payloads retain full identity collision checks. Identity includes geometry, base segment timing, departure minute, directed stops/waits and provider/avoidance settings. It excludes vehicle fuel consumption, trip history ID and unrelated hazard answers. Overlaying a reused profile still derives energy from the current vehicle model.

Fresh complete analyses bypass route matching/traversal and create no traffic-work task. Window screening loads these results before counting missing work or asking about traffic refresh. Unchanged approved combinations require no traffic analysis; changing windows or approval responses analyzes only newly needed combinations and reuses the overlap. Weather checks and consent decisions remain authoritative; a saved traffic profile never approves a changed hazard. If a new combination shares road sections with old ones, the existing piece matcher requests only missing/expired compatible sections.

Traffic freshness remains governed by its existing preset, independently of rest-site data refresh days. Explicit force/fresh-after requests bypass old analyses. Failed or incomplete profiles do not become successful completed analyses. Original observation timestamps survive reuse; cache clearing cancels late writes. The analysis store has its own 8,192-record/256 MB bound, so it does not evict provider-piece records. Tests exercise restart with zero analyses, one added hour with exactly one analysis, narrowed/rejected hours with none, incompatible timing, explicit bypass, and section-level incremental reads after removing aggregate fixtures.
